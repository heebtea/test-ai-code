## 跳過 22 筆的根因與證據界線

main `ceaff60` 的舊程式有三個過寬判重路徑：

1. `ocr-review.js`：recommended + action=skip，只要已有同日期同類別就直接跳過，未比較數值。
2. `ocr-records.js`：同日期同類別且 action=skip，全部跳過。
3. `duplicateConfirmed()`：以名稱＋時間等有限欄位當確認重複，忽略金額、數量、說明等差異。

此外，舊 `main.js` 把 `unselectedSkipped` 加入已處理的 skipped，使未選候選混入跳過總數，且結果沒有逐筆原因。

可重現測試保留歷史 planner 原碼（只調整 import 路徑）於 `tests/fixtures/legacy-ocr-*.js`：一筆既有睡眠 300 分鐘，輸入 22 筆同日、400～421 分鐘的合成候選。舊程式結果 **0 新增／22 跳過／0 草稿**；新程式 **0 新增／0 重複／22 待確認**，每筆解釋「同日數據內容不同」。既有紀錄不變。

另以混合 22 筆合成資料測試（[逐筆決策表](ocr-synthetic-decisions.md)）：**5 新增／3 完全重複／14 待確認／0 失敗**；重匯只跳過已存在內容，不新增或覆寫。這兩個情境證明缺陷與修復，但**不代表使用者歷史那 22 筆的個別原因已還原**；當時 localStorage、候選明細及逐筆日誌未提供，本次也不使用真實私人資料。

## 完整備份安全與遷移

- 外層格式 `second-brain-lite-complete / backupVersion=1`；生活紀錄使用獨立 schema v7。模板及照片以 JSON＋Base64 搬移，設定只有深淺色與目前選取模板，沒有憑證。
- 讀取舊資料不寫回。新修改升 v7；完整還原保留原 ID、舊欄位及未知值，不替舊紀錄編造來源或修改時間。
- 不接受未知版本、破損 JSON、非法欄位／日期／數量／ID、非法圖片格式、重複 ID 或孤兒照片；逐筆可診斷的錯誤放入預覽，確認後只寫合法選項。
- 預設不覆寫，相同 ID 衝突須逐筆明確選取備份版本。圖片／模板依賴也受保護，不因保留本機紀錄卻把其照片換成衝突匯入照片。
- 預覽保存內容指紋，確認時重新比較；在 Web Lock 下先把 undo 快照寫入專用 IndexedDB，再進行照片、模板、localStorage 寫入，最後寫 committed 標記。失敗回復被觸及的項目；啟動時恢復未完成交易或清理已完成日誌。
- 回復本身失敗時保留日誌並停止寫入。不要清除瀏覽器儲存；恢復可用空間後重開。僅支援新版合作分頁；還原前先關閉舊版分頁。
- 同一裝置仍可能遭使用者清除網站資料、瀏覽器驅逐或裝置損壞；本機回復日誌不能取代外部備份。100 MB JSON 上限、單圖 10 MB；Base64 與 undo 快照需要額外空間。
- v7／完整備份無法回匯 v0.4；部署若未來獲准，先備份再升級，不能在寫入 v7 後直接退回舊程式。

## 雲端同步設計比較（尚未實作）

| 方案 | 優點 | 代價／仍須解決 |
| --- | --- | --- |
| 本次完整檔案搬移 | 無新帳號、無後端、使用者控制資料傳送；現在可用 | 手動操作、檔案未加密、無即時同步 |
| 使用者私有雲端空間＋OAuth | 資料由使用者自己的空間管理，可撤銷授權 | 需要另行選服務與授權；照片分塊、版本衝突、離線佇列、裝置金鑰與權限範圍待設計 |
| 私有同步後端＋物件儲存 | 可逐筆同步、保留版本與稽核、處理多人多裝置併發 | 必須建立帳號／每使用者存取隔離、照片私有權限、傳輸與靜態加密、備份及費用管理 |

建議先驗收本次完整搬移，再選一種私有同步路線。未來同步需保持 record ID、基底版本與修改版本；不能僅依時間戳最後寫入覆蓋。衝突要保留雙方版本，刪除需可回復的刪除標記，付款／攝取永不依名稱自動合併。若採用客戶端加密，另需設計密鑰備份、換機與遺失復原。公開 GitHub／GitHub Pages 不作私人紀錄儲存；任何後端、帳號授權或 CSP 外部端點變更另行審查。
