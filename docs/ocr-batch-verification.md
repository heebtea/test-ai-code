# OCR 批次匯入修復驗證

基底：`ceaff606c6f1c9656bd049dea4948233aa662f87`。本次只修批次決策、結果原因與測試，不重寫 OCR 引擎，不修改正式站部署流程。

## 調查與證據限制

雲端無法讀取使用者裝置的 localStorage，也沒有原本 22 筆候選及逐筆決策日誌，因此不能斷言那 22 筆都是重複，或聲稱已還原每筆歷史原因。可從基底程式確認的錯誤路徑：

1. `ocr-review.js` 對 recommended + skip，只要同日同類存在就直接跳過，未核對數值。
2. `ocr-records.js` 的 skip 也以同日同類為判準，未比較完整內容。
3. `duplicateConfirmed` 對餐飲／事件只比較類別、日期、去空白名稱、時間，會忽略金額、付款／食用狀態、容量與備註差異。
4. `main.js` 以同日同類設定 duplicate，且把未選取的 conflict 也加進跳過數。即使沒有執行該筆匯入，也會列為已跳過。
5. 部分錯誤只被 catch，結果沒有逐筆原因，無法事後追查。

修復後逐筆回傳 `index / kind / code / reason / recordId`，總確認與完成畫面均顯示結果原因及重複目標 ID。只計算本次實際選取的項目；未選項目獨立顯示。完全相同的正式紀錄或同來源同內容草稿才列為重複。

## 決策與資料安全

- 所有正式紀錄欄位逐項比較，排除 ID；只對舊格式可省略的欄位做相容處理，沒有模糊名稱比對。
- 合法新資料在核對與總確認後才進正式紀錄。同日數據內容不同先存草稿，保留手動合併空白或另存的既有選項。
- 分類不明、格式不全、尚未核對、付款或食用狀態不明，保留候選與來源為待確認草稿；不轉成餐點、不納入統計。
- 同日同額的付款可能同時出現在餐飲區及花費區，保守保留為草稿，避免重複記帳；不把訂購推定為付款或食用。
- ID 衝突及錯誤草稿 ID 不覆寫既有資料；單筆失敗不阻止後續項目。原有跨分頁與儲存失敗保護保留。
- v2～v6 JSON 讀取、原紀錄保留、草稿匯出／回匯測試通過。草稿沿用現有 v6 格式；沒有加入真實預設數據。
- 測試資料完全虛構；未提交使用者圖片、小誌、localStorage、截圖或真實生活紀錄。
